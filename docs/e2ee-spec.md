# End-to-end encryption specification (format version 2)

This is the byte-level contract for Maple Notes' key-derived sign-in and end-to-end encryption (E2EE). The web app
(`src/maple-web/src/crypto/`) implements it, and so does an independent C# implementation in the test suite
(`tests/MapleNotes.Server.Tests/TestSupport/E2eeCrypto.cs`). Both must reproduce the committed test vectors in
`src/maple-web/src/crypto/test-vectors.json` exactly. Server-side encryption at rest (format version 1) is described in
[architecture.md](architecture.md#cryptography).

## Conventions

- **Text:** UTF-8. Passwords and tag names are Unicode-normalized to NFC first.
- **IDs:** in contexts, IDs are written as 32 lowercase hexadecimal digits without dashes (a UUID's "N" format).
- **HKDF:** HKDF-SHA256 (RFC 5869) with an **empty salt** unless stated otherwise, and the label below as `info`. All
  keys are 32 bytes.
- **Binary in the API:** standard base64 with padding. Tag tokens use base64url without padding.
- **Client-chosen IDs:** new E2EE notes and attachments use UUIDs version 7 (RFC 9562) generated by the browser,
  because the ID is bound into the ciphertext. The server rejects IDs that are not version 7, whose timestamp is more
  than 24 hours from its own clock, or that are already in use.

## 1. Password-derived keys (every account)

```text
master   = Argon2id(password = UTF-8(NFC(password)), salt, m, t, p, length 32, version 0x13)
authKey  = HKDF(master, info "maple-notes/v2/auth")
wrapKey  = HKDF(master, info "maple-notes/v2/wrap")
```

- **Parameters:**
  - The salt is 16 random bytes per account.
  - Defaults are `m = 65536` KiB (64 MiB), `t = 3` passes and `p = 1` lane.
  - Clients and the server reject `m < 19456`, `t < 2`, `p` outside 1–4, `m > 1048576` and `t > 10`. The minimum
    matches OWASP's baseline for Argon2id.
- **Where the keys go:**
  - `authKey` is the sign-in credential. The server stores it only as a PBKDF2-HMAC-SHA512 hash (ASP.NET Core
    Identity v3, 210,000 iterations), computed over its base64 text.
  - `wrapKey` never leaves the browser.
- **Prelogin:** the browser learns the salt and parameters from `POST /api/v1/auth/prelogin` (`{ "username" }` →
  `{ "kdf": { "salt", "memoryKiB", "iterations", "parallelism" }, "upgrade" }`). It is rate-limited per client IP
  like sign-in, with a separate budget.
  - For an unknown username, the server answers with the default parameters and a deterministic pseudo-salt:
    `HMAC-SHA256(preloginKey, UTF-8(trimmed, upper-invariant username))`, first 16 bytes. `preloginKey` is derived
    from the instance master key like the other instance keys (HKDF label `maple-notes/v1/prelogin`, see
    [architecture.md](architecture.md#key-hierarchy)); it is internal to the server, so this step is not part of the
    cross-implementation vectors. The answer therefore looks the same whether or not the account exists, and stays the
    same across requests.
- **Registration and password changes:** the browser picks a fresh random salt and the default parameters and sends
  them with the new `authKey`. A password change also proves the current password (below).
- **Proof of the password:** security-relevant changes (password, encryption settings, deleting the account) carry
  `{ "authKey", "password"? }`, derived with the account's parameters from prelogin.
- **Legacy accounts** (created by version 1.0, holding a hash of the password itself) have their stored hash kept and
  receive a random salt and the default parameters when the database is upgraded; prelogin answers `upgrade: true` for
  them. The next sign-in or proof then sends the password once together with the new `authKey`: the server checks the
  password against the old hash and replaces it with a hash of `authKey`. Until that happens, `upgrade: true` reveals
  that the account exists; this is the only exception to the rule above, and it ends at the owner's next sign-in.

## 2. Envelope (AES-256-GCM)

Identical to the server's version 1 envelope:

```text
[0]      format version = 1
[1]      key version    = 1
[2..13]  nonce (12 random bytes)
[14..29] authentication tag (16 bytes)
[30..]   ciphertext
AAD = bytes [0..1] ‖ UTF-8(context)
```

| Payload | Key | Context |
|---|---|---|
| Data key, wrapped by password | `wrapKey` | `maple-notes/v2/e2ee/data-key/{userId}` |
| Data key, wrapped by recovery key | `recoveryWrapKey` | `maple-notes/v2/e2ee/recovery/{userId}` |
| Note text (UTF-8 Markdown) | `noteKey` | `maple-notes/v2/e2ee/note/{userId}/{noteId}` |
| Tag name (UTF-8) | `metadataKey` | `maple-notes/v2/e2ee/tag/{userId}/{token}` |
| Attachment metadata (JSON) | `metadataKey` | `maple-notes/v2/e2ee/attachment-meta/{userId}/{attachmentId}` |

The plaintext of a wrapped data key is exactly its 32 bytes.

## 3. The E2EE data key and its subkeys

The data key is 32 random bytes generated in the browser when E2EE is switched on. It never leaves the browser
unwrapped.

```text
noteKey      = HKDF(dataKey, info "maple-notes/v2/e2ee/note")        AES-256-GCM
metadataKey  = HKDF(dataKey, info "maple-notes/v2/e2ee/metadata")    AES-256-GCM
tagIndexKey  = HKDF(dataKey, info "maple-notes/v2/e2ee/tag-index")   HMAC-SHA256
fileKey      = HKDF(dataKey, salt = file salt, info "maple-notes/v2/e2ee/attachment")
```

In the browser the data key is imported as a non-extractable HKDF key, and the subkeys are derived as
non-extractable `CryptoKey`s.

## 4. Tags

- **Which words are tags:** the same rules as the server's tag parser. A `#` is not preceded by a letter, digit,
  `_`, `/`, `#` or `&`, and is followed by a letter, digit or `_`. Tags continue with letters, digits, `_`, `/` and
  `-` (64 characters at most). Trailing `/` and `-` are dropped, purely numeric tags are ignored, and tags inside
  inline or fenced code are ignored.
- **Normalization:** NFC, then JavaScript's `toLowerCase()` (Unicode default case mapping).
- **Token:** `base64url(HMAC-SHA256(tagIndexKey, UTF-8(normalized name))[0..16])`, which is 22 characters.
- **Storage:** the server stores the token, the note–tag links and the encrypted tag name (§2). It can filter and
  count by token but never learns the name.
- **Nested tags:** filtering by `work` sends the tokens of `work` and of every known tag below it (`work/…`). The
  browser knows these from the decrypted tag list.

## 5. Attachments

**File format:** the same chunked format as server-side encryption:

```text
header (42 bytes) = "MNAE" | 0x01 | key version 0x01 | chunk size (uint32 BE, 65536) | 32-byte random salt
chunk i           = ciphertext (≤ 65,536 bytes) ‖ 16-byte tag
nonce of chunk i  = 7 zero bytes | i (uint32 BE) | final flag (0x01 for the last chunk, else 0x00)
AAD of every chunk = header ‖ UTF-8("maple-notes/v2/e2ee/attachment/{userId}/{attachmentId}")
```

Every chunk except the last holds exactly 65,536 bytes of plaintext. An empty file is one final chunk of 16 bytes (the
tag alone).

**Metadata:** `{"name": "...", "type": "...", "size": 123}` as UTF-8 JSON, sealed with `metadataKey` (§2). The
server stores the file as `application/octet-stream` with a placeholder name and knows only its encrypted size.

## 6. Recovery key

```text
recoveryKey      = 32 random bytes
displayed        = Crockford Base32 of the 32 bytes (52 characters, 4 zero padding bits), 13 groups of 4 joined by "-"
recoveryWrapKey  = HKDF(recoveryKey, info "maple-notes/v2/recovery/wrap")
recoveryAuthKey  = HKDF(recoveryKey, info "maple-notes/v2/recovery/auth")
```

- **Alphabet:** `0123456789ABCDEFGHJKMNPQRSTVWXYZ`.
- **Parsing:** ignores case, spaces and dashes, reads `O` as `0` and `I`/`L` as `1`, and rejects anything that does
  not decode to exactly 32 bytes with zero padding bits.
- **Server storage:** the data key wrapped with `recoveryWrapKey` (§2), and a PBKDF2 hash of `recoveryAuthKey`,
  which proves knowledge of the recovery key when resetting a forgotten password.
- **After a recovery:** the browser generates a new recovery key.

## 7. Test vectors

`src/maple-web/src/crypto/test-vectors.json` fixes every input: the password, salts, nonces, data key, recovery key,
IDs and a two-chunk attachment. It also records every output: the derived keys, the envelopes, the tag token, the
displayed recovery key, and the SHA-256 of the encrypted attachment. The vectors use the minimum Argon2 parameters so
the tests stay fast. The C# test (`tests/MapleNotes.Server.Tests/E2ee/E2eeVectorTests.cs`) regenerates the file when
`MAPLE_WRITE_VECTORS=1` is set and otherwise verifies it; the TypeScript test (`src/maple-web/src/crypto/vectors.test.ts`)
verifies it with the browser code.
